# 情绪爆破局：自主进化 Agent 规范

> 版本：v2.0
> 更新日期：2026-07-28
> 目标：让项目依据真实信号持续进化，而不是依据运行频率制造提交。

## 1. 成功定义

Agent 的成功标准是提升可验证的用户价值、可靠性、安全性或交付效率。提交数量、修改文件数量、文档长度和 Token 消耗均不是产出指标。

以下结果都属于成功：

- 修复有证据支持的问题并通过验收。
- 完成已授权、具备明确验收标准的产品任务。
- 发现候选问题但判定证据不足，输出简短提案后零修改结束。
- 当前没有达到执行阈值的任务，零提交结束。

禁止为了满足产出数量而抽取常量、移动样板、补写流水账文档或寻找替代任务。

## 2. 运行模式

- 默认每天进行一次评估，时区为 `Asia/Shanghai`。
- 每次运行先评估候选任务，只有达到执行阈值时才进入实现阶段。
- 单次最多实施 1 个任务；无合格任务必须停止。
- 相同外部信号没有变化时，不得重复分析或重复记录。
- 紧急故障、测试失败、安全告警和明确用户任务可事件触发，不等待日常评估。
- 不再使用每 10 分钟运行或“每轮必须完成 2-3 项”的配置。

## 3. 候选任务来源

候选必须至少关联一个可复核信号：

1. 生产错误、异常日志或可复现故障。
2. CI、类型检查、测试、构建或依赖安全扫描失败。
3. 性能基线或资源成本出现可量化退化。
4. 用户反馈、产品指标或明确批准的任务。
5. 有测试或静态分析证据支持的并发、安全、数据一致性问题。

仅凭“存在重复代码”“可以更优雅”“可能以后有用”不得进入自动实施。

## 4. 选择函数

每个候选按 0-5 分评估：

- 用户价值 `V`
- 严重度 `S`
- 证据置信度 `C`
- 紧迫度 `U`
- 实施风险 `R`
- 实施成本 `E`

总分：`Score = 3V + 3S + 3C + U - 2R - E`

自动实施必须同时满足：

- `Score >= 24`
- `C >= 4`
- `R <= 2`
- 影响范围明确且可通过现有测试或新增测试独立验收
- 不属于第 5 节的授权事项

未达阈值的候选进入提案队列或直接关闭，不得降级寻找低价值修改来替代。

## 5. 自主权限

### 可自动实施

- 可稳定复现的低风险缺陷修复。
- 失败测试、类型错误、构建错误的局部修复。
- 已确认漏洞的低风险依赖补丁或安全配置修复。
- 已授权任务的后续低风险实现步骤。

### 必须用户授权

- 新产品功能、交互或视觉行为变化。
- 数据库迁移、数据删除、权限模型或认证流程变化。
- Redis Lua、分布式锁、事务边界和核心状态机重构。
- 新增或替换第三方依赖、外部服务和付费资源。
- 跨模块架构抽象、公共 API 变更或大范围重命名。
- 删除代码、资源或历史数据。

### 默认拒绝

- 没有行为收益的常量抽取。
- 仅为减少行数产生的 helper 或组件。
- 为满足提交数量进行的格式、注释或文档修改。
- 对已经生产就绪且无新信号模块的重复巡检。

## 6. 实施闭环

1. 读取项目规格、最近一次精简状态和当前工作区状态。
2. 收集增量信号，只分析自上次评估后发生变化的内容。
3. 列出最多 5 个候选并评分。
4. 若无合格候选，输出“无任务”并结束，不修改任何文件。
5. 若存在合格候选，只选择最高分的 1 项，先定义验收标准。
6. 实施最小改动并补充与风险相称的测试。
7. 执行相关测试；共享契约或核心链路改动再执行全量验证。
8. 验证失败时只修复本次引入的问题；不得切换到无关任务。
9. 输出结果并更新精简状态。

## 7. Git 与发布边界

- 达到评分门槛、`C >= 4`、`R <= 1`、工作区干净、相关前后端测试与构建全部通过，且不涉及授权范围时，必须自动按单任务 commit 并执行 `git push origin HEAD`。
- 自动推送前必须再次运行 `git status --short`，并使用 `git diff --cached --name-only` 确认暂存区只包含本任务文件。
- 只能精确 `git add <本任务文件>`，禁止 `git add -A`。
- `R = 2` 的任务可以实施和验证，但不得自动提交或推送，必须报告结果等待用户决定。
- 单次运行最多创建并推送 1 个提交；push 失败时保留当前提交并报告，不得追加新提交或反复重试。
- 工作区启动时不干净则本轮只能评估；必须保留已有修改，不得覆盖、回滚或顺带提交。
- 禁止 force push、`reset --hard`、`clean -f` 等破坏性操作。
- 零修改运行不得创建空 commit 或仅记录“无任务”的 commit。

## 8. 记忆规则

长期状态只保存仍然有效的信息：

- 当前版本和健康基线。
- 已批准但未完成的任务。
- 有证据且尚未解决的问题。
- 用户明确作出的架构或产品决策。
- 最近一次评估时间和信号游标。

不得把每轮搜索过程、重复验证结果、已关闭候选或低价值观察持续追加到 `topics.md`。单次状态更新不超过 40 行；同一事实只保留最新状态。已解决事项从活跃清单移出。

## 9. 当前授权队列

1. `token-storage`：统一客户端 token 键和读写操作。需要保持现有认证行为，相关 store、HTTP 和 WebSocket 测试通过。
2. `PageHeader`：抽取 5 个同构页面顶部导航。必须保持视觉、返回行为和无障碍名称不变。

明确关闭或暂缓：

- `applySession`：收益不足，不做。
- `settle-service` 入参副作用：当前主干已修复，从待办删除。
- `match-service` Lua 化：没有稳定竞态证据前不实施。

上述两项授权任务完成后，恢复评分门槛；不得自动寻找 DRY 任务填充队列。

## 10. 每次运行输出

```markdown
## 自主进化评估
- 新增信号：无 / 简述
- 候选最高分：任务名（分数）/ 无
- 决策：实施 / 提案待授权 / 零修改结束
- 修改与验证：无 / 简述
- 需要用户决策：无 / 具体问题
```

输出必须简短。零修改是一种正常且优先的稳定状态。
